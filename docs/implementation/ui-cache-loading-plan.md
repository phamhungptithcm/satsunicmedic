## Verified findings

- `packages/anatomy-viewer/src/verified-body-asset.ts` uses no-store on every model fetch, verifies size/SHA-256, and has no byte cache. Returning to a disposed chunk can download and verify the same public bytes again.
- `full-body-canvas.tsx` already limits downloads to two, retains current/return chunks and disposes unused geometry. Each completed chunk calls apply then reconcile; reconcile calls apply again, and apply renders. Coalescing redundant work is preferable to reducing geometry.
- `packages/api-client/src/index.ts` has a ten-second timeout and cancellation but no shared pending-operation indicator. Requests include public reads, private data and writes, so global response caching would be unsafe.
- Existing route/dynamic Loading components use an indeterminate ornament. Long actions in teaching, quizzes, study, account and directory components have separate busy states; there is no uniform progress bar or complete action inventory.
- Explorer disables query retention (staleTime/gcTime zero). Do not blanket-enable caching: the same surface loads identity and private notes as well as public assets.
- Linux CI at 8d05109 loaded the whole body and passed model actions; macOS headless timed out. This is environment-specific evidence, not an established production renderer defect.

Repository intelligence DEGRADED from stale optional indexes; bounded source, current tests and CI/browser evidence used. Read installed Next.js linking/loading/caching guides before framework changes. Do not infer current API behavior from an older Next.js version.

## Proposed interaction

A thin blue bar appears at the top while navigation or requests remain pending. The active section or button shows a short contextual label (for example Đang tải mô hình, Đang tìm cơ sở, Đang lưu bài). Existing usable content stays visible when its meaning remains accurate. Disabled repeated-submit controls prevent duplicate writes; cancellation and errors clear pending state and offer a relevant retry.

Model download progress uses actual verified-manifest byte totals, counting cache hits as available bytes. After download completes, use an indeterminate bar labeled Đang dựng mô hình until parsing/render readiness; never show a fake percentage or 100% completion while the model is unusable. Unknown-duration operations use indeterminate bars. Respect reduced motion, screen readers, keyboard focus and mobile layout. Avoid duplicate live announcements or an overlay blocking unrelated controls.

## File-by-file implementation

1. `packages/anatomy-viewer/src/verified-body-asset.ts` plus a focused cache helper if needed: bounded in-tab LRU cache of verified public model bytes, keyed by URL + SHA-256 + byte length, initially 32 MiB and five-minute expiry. Verify before insertion, return isolated byte buffers, deduplicate matching in-flight downloads, track subscribers so one cancellation cannot cancel another active consumer. Abort underlying work when no subscribers remain; do not cache failed, partial or cancelled results. Evict by byte size and clear stale entries. No persistent private storage, whole-atlas prefetch or model simplification.
2. `anatomy-model-loader.ts`, `full-body-canvas.tsx`, `apps/web/src/components/full-body-anatomy.tsx` and relevant simulation canvas/panel callers: propagate optional progress callbacks; aggregate only the current scene generation; batch redundant render/apply work per animation frame with cleanup on unmount. Preserve hash verification, source identities, geometry, selection, clipping, material appearance and disposal ownership. Do not share cached mutable THREE objects between consumers.
3. `packages/api-client/src/index.ts` and a small pending-request store: register browser-side pending operations and settle exactly once in finally on success, failure, abort or timeout. Keep response semantics, CSRF and cache:no-store for private data and mutations. No global fetch monkey patch, endpoint logging or optimistic success. Server requests must not share user-visible pending state across requests.
4. `apps/web/src/components/loading.tsx`, `loading.module.css`, a small app-level request/navigation progress component, `app/layout.tsx`, `app/loading.tsx`: compact measured/indeterminate bar variants and shared pending feedback. Use supported installed Next.js APIs/loading boundaries; avoid guessed navigation completion or timers that imply success. Threshold a fast request to avoid flicker, but never delay the actual operation or hide a long-running action.
5. Audit components using request/fetch, dynamic imports, file export or model loading. Integrate the shared indicator and contextual busy states in teaching-workspace, personal-study, learning-reviews, quizzes, facility-search, explorer and account/session components as needed. Produce an action coverage matrix listing each operation and its success/error/cancel/timeout behavior. Preserve filters and content association; do not show old province results as current new-filter results. Do not cache private response bodies or authentication decisions in this scope. Any public response-cache addition needs source-specific invalidation evidence first.

Tests: bounded cache hit/expiry/eviction/integrity; simultaneous subscribers; cancellation/timeout; no cache poisoning or mutation leakage; progress aggregation across scene changes; pending counter cleanup and concurrent requests; no background request stuck at completion. Extend browser acceptance for cold/warm navigation, throttled model and API loads, error/retry, duplicate-submit prevention and reduced motion.

## Scope and risk

Medium/high risk: async cancellation, memory ownership, multi-request state and UI privacy. Keep public model byte caching separate from private/user-specific responses. No server cache header change, auth/rules/schema/IAM change, extra paid services, model reduction or hidden request prefetch. Existing budget gates and native spend caps remain. This plan optimizes repeat loads; it does not promise a fast initial download on every connection or that a loading bar alone fixes main-thread stalls.

Acceptance: warm cached chunks generate fewer network requests; bounded memory/cache entries; all assets retain the same hashes; current acceptance controls and full body remain usable; pending feedback is visible for delayed operations and always settles; errors remain actionable. Compare the same browser/device and same asset selection for cold/warm evidence. Run focused regression, typecheck/lint/build, existing integration checks where the request wrapper is affected, and full current-candidate CI before production promotion. Final review must distinguish source checks from live OAuth, physical-device and full-product acceptance.

Rollback: revert the scoped UI/cache commits and redeploy the verified predecessor via the existing pipeline; no data migration or deletion. New source changes invalidate prior exact-SHA acceptance and must receive fresh receipts. Current production remains unchanged while this work is prepared.
